## Decisions that bind the design (Andrew's)

- **Pure MIME types.** An answer has `mime` and `topLevel` (the registry's word before the slash). There is **no** `IMAGE`/`DOCUMENT`/`ARCHIVE` kind in `mimedown`; I added one, he found it confusing, and it was removed. He maps types to his `AssetType` enum in a TypeScript helper of his own ("TEXT = always document, APPLICATION = often document"). Do not reintroduce a kind.
- Never a MIME type as an argument; no guessed-type field; `UNKNOWN` is an answer, not an error.
- The file name is a hint for text only.
- `mimedown` depends on `pdfdown` (behind `pdf`) for word count, preview and searchability; the PDF metadata derivation is to move into `pdfdown-meta` later.
- Fonts, models and haptics exist as types (`font/*`, `model/*`, `haptics/*`); `model/vnd.pixar.usd` is his ask and is not registered.
- `.ai` files are PDFs and are named `application/pdf`.

## `retryOnUnknown` and the end-to-end exchange tests: done

Built, checked on real files, and written into the plan as "`retryOnUnknown` and the exchange, as built" under section 10. Reported to Andrew.

- **End to end:** `specs/exchange_tests.rs` drives a fetcher's loop (head, then each `needs`, until none) over every format from heads of 16, 300 and 4,096 bytes with the size known and unknown. All settle within 8 fetches on the whole-file answer. They passed with no code change.
- **Second look,** only when `retry_on_unknown` is set and the first pass names nothing:
  1. Behind up to 1,024 leading bytes, by `STRICT_TESTS` only: `checked_png` (the header chunk's checksum must hold, `png::header_holds`), `declared_elements` (EBML that names its document type), `streams` (a compound file that parses). **A bare signature is never enough there.**
  2. At the end (`at_the_end`): a zip by its directory (`zip::start_from_end`, `zip::listing_by_directory`; offsets counted from the zip's start or the file's; at least one entry), a PDF by `startxref`, a number, `%%EOF` in order (`ends_as_pdf`), with `pdf_header_at` saying how many bytes stand in front, and an MP3 by `TAG` 128 bytes from the end.
  3. Text read leniently (`text::decode_leniently`): UTF-16 with no mark, or under one stray control byte in a thousand.
- `Retry::{LeadingBytes { skipped }, EndOfFile, LenientText}` says which. `specs` reads facts from `source.shifted(leading)`.
- **Why the rule is strict:** on real files, MPEG's four bytes turned up by chance behind leading bytes, and two compiled Python modules (the PNG and GIF readers) were named PNG and GIF because they hold those signatures as constants. Each fix was test first. The last run: 29,011 files, 15 named by a second look (4 zips at the end of Windows libraries, 11 texts with a stray control character), none of 4,243 compiled Python modules.
- The test builder `png_chunk` now writes real checksums.
- **Not found by a second look, by design:** GIF, JPEG, RIFF, sound, or archives other than zip behind leading bytes. Offered to Andrew as a possible widening (count a bare signature when what stands in front is blank or text) if his files show a need.
