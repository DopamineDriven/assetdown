## 4. What was built since the last note

### `ocrdown`, `tiffdown`, `jpegdown`

Format-agnostic Tesseract code lives in `ocrdown` (`recognize_page`, `PagePicture`, `Thresholding { Global, Adaptive }`, `enlarged` to 200 ppi, `in_order`, `ready`). `pdfdown-ocr`, `tiffdown` (feature `ocr`), and `jpegdown` (feature `ocr`) use it. `tiffdown-node` and `jpegdown-node` each have a base package and an OCR superset package in `ocr/`. `tiffdown` 0.1.0 predates later `ocrdown` improvements (a per-page choice of thresholding, and no enlarging of a page already near 200 ppi): a `tiffdown@0.2.0` would ship them.

### `pdfdown`: two fixes

- **0.19.0**: `lopdf`'s `extract_text` is gone. A page's text is the lines of its layout (`crates/pdfdown/src/text.rs`: `text_of_layout`, `page_text`, `extract_text`). This fixed `textPerPage` returning nothing for text inside forms, and `mimedown`'s `isSearchable`. Confirmed by the user's full run.
- **0.20.0**: an endless loop in `crates/pdfdown/src/layout/tounicode.rs`. The tokenizer's fallback arm stopped a word at any delimiter, and every delimiter but `)` had an arm that moved past it; a stray `)` gave an empty word forever and filled memory. Now:

```rust
b'>' | b')' | b'{' | b'}' => i += 1,
// ... and in the fallback arm, after taking the word:
if i == start {
  i += 1;
  continue;
}
```

Tests: `a_closing_parenthesis_with_nothing_to_close_is_passed_over` and `no_byte_holds_the_tokenizer_in_place` in `layout/tounicode/tests.rs`. To watch such a test fail safely, build the test binary first, then run it under `ulimit -v 2000000` and `timeout`. A like test guards `rtfdown`'s tokenizer (`no_byte_holds_the_tokens_in_place`).

### `rtfdown` (library)

`crates/rtfdown/src`: `token.rs`, `cfb.rs`, `rtf.rs` (`Rtf::open`, `embedded`, `pictures`, `text`, `blocks`, `paper`, `running`, `layout`, `invoice`, `warnings`), `body.rs` (the reader and the model), `layout.rs` (pages). Notable behavior, all tested (64 tests):

- A paragraph the file places (`\posx`, `\posy`, `\absw`, with `\phpg`/`\pvpg`) is set at that place. Paragraphs one after another with the same frame properties are one frame and stack (`Paragraph::continues_frame`); a frame that differs in anything, its height included, is another.
- Space before and after a paragraph is what the file states (`\sb`, `\sa`), and none where it states none. There is no estimated gap.
- Headers and footers (`\header`, `\footer`, `\headerr`, `\footerr`, and with `\titlepg` the first page's `\headerf`, `\footerf`) are read apart (`Running`) and set on every page; they are not in `text()`. The first stated of each kind wins; one for left pages is passed over.
- Not read yet: tab stops, line spacing, row heights, room for a picture, text boxes, Markdown.

When checking RTF against LibreOffice: its text export leaves out framed text, and its PDF drops lines that overflow a frame. Count words against `--convert-to odt` and the text of `content.xml` (memory: `heif-tools-installed`).

### `rtfdown-node` and the WebAssembly pilot

`crates/rtfdown-node` exports `rtfText`, `rtfLayout`, `rtfInvoice`, `rtfEmbedded`, `rtfPictures`, `rtfDocument`, each with an `Async` twin, and class `RtfDown`.

`crates/rtfdown-node/wasm/` is a second, self-contained npm package, `@d0paminedriven/rtfdown-wasm`, published at 0.2.0. Read section 6 of `BRAINSTORM/phase-two/config-updates.md` and `wasm/README.md` before touching it. The shape:

- Two builds in one package: with threads (`wasm32-wasip1-threads`, named `wasm32-wasi` by napi) and without (`wasm32-wasip1`). They are the same WASI version; the second is not older.
- Its entries are the builds' own loaders, not napi's generic root entry, so the type of `__napiBindingTarget` is exact and nothing looks for a native addon. Built with `--no-js`. The manifest is kept by hand, with `exports` for `.`, `./threads`, `./threadless`, `./workerd`, `./wasm`, `./wasm.wasm`, and `./worker`.
- `./worker` is a Web Worker entry, browser only: `wasm/src/protocol.ts` (the user's key-indexed types: `BindingRT<K>`, `BindingArgs<K>`, `AsyncBindingKeys`, `SyncBindingKeys`, with `Awaited`), `worker.ts`, `client.ts` (`RtfWorker implements PageVerbs`, methods named as the binding's promise verbs), `buffer.ts` (a stand-in for `Buffer`, imported first). Bundled by `wasm/tsdown.config.ts` in the user's convention, with `rolldown-plugin-wasm` and a `?url` import; the worker starts the build through napi's deferred loader.
- Tests: `wasm/__test__/` (25 tests, 4 of them in the installed Chrome through `playwright-core`), run by `yarn test:wasm` after `yarn build:wasm-package`. `tsdown` is run as `cd wasm && ../node_modules/.bin/tsdown`, because yarn refuses a folder with a manifest that is not a workspace.
- CI: `crates/rtfdown-node/ci/wasm` and `ci/publish-wasm`, jobs `wasm` (Node 26 and 24) and `publish-wasm` in `.github/workflows/rtfdown-node.yml`. `version.sh rtfdown` moves four files, `wasm/package.json` among them.
- Findings worth keeping: a page has no `Buffer`, so a verb that returns bytes throws there without the stand-in (the direct page entry is not fixed; the user declined a Rust-side change). `NAPI_RS_WASI_FLAVOR` is process-wide and breaks other napi packages that ship one build. A worker must listen before it awaits anything, or early messages are lost. A server that does not label `.wasm` stops stream compiling, so the worker falls back to the whole file.
- Not done: a Node build of the worker, a parsed-document handle across the worker, a copy command like the user's `sttworklet`, other browsers and bundlers, and rolling the pattern out to other packages (`mimedown` is the obvious next one).
